## 1. 审查结论与 V1.1 改进范围

原20张主画板覆盖购买、记录、回顾、领取、会员和设置的主要路径。主要缺口在首次授权、交易失败与未知结果、免费用户入口、资料管理及异步任务状态、历史订单与工单追踪。V1.1 按以下原则补齐：

- 补任务和关键异常，不改变组合会员、每已付账期一次自主领取、正常到期不自动结转的产品基线。
- 支付、服务生效、权益发放、领取、发货、退款到账及外部解约分别表达，不用一个成功页面替代不同事实。
- 保留拒绝授权、手动记录、只在站内提醒、单期主动付款和数据权利路径。
- 用状态表补足栅格稿没有表现的分支；每张图至少对应原 PRD 功能、状态及验收用例。
- 统一可实施的字体、颜色、控件和错误反馈规则。正文对比度目标至少4.5:1；主要动作色 `#B74752` 配白字约5.20:1，在暖白底上的同色文字约4.95:1，最终组件仍需真机测量。

## 4. 必须配套的状态与实施说明

### 4.1 数据权利任务

- 导出：未提交→已受理/生成中→可下载；另有生成失败与下载失效。下载校验本人，过期文件不得通过旧链接访问。
- 删除：确认范围→受理并终止相关访问/任务→清理中→完成或待处理失败。交易留存不是继续保留全部健康原文的理由，也不承诺所有备份即时销毁。
- 注销：说明影响及未决事项→受理→停止新收费/停止健康访问→必要交易与协议善后→完成。受理后进度查看采用限定范围的安全方式，不恢复全部账户数据访问。
- 撤回AI授权：停止新任务，取消或丢弃在途返回；手动记录、独立权益与交易管理不因此取消。

### 4.2 提醒与工单

提醒状态按 PRD 映射 `scheduled / sending / accepted / failed / unknown / canceled`。用户看到的“已预约”“平台已接收”“结果待确认”“已取消”必须对应实际事实；不能由一次授权推导无限月度发送，也不能改走未经同意的短信渠道。

工单列表和详情给出编号、分类、关联业务单、受理时间、最新处理状态及说明。未知提交先查询原请求，避免重复工单；“受理”不等于“已解决”。本轮不新增即时聊天和固定解决时限。

### 4.3 数据与统计语义

U08 示例为4次开始、3段完整记录；相邻开始间隔28/29/28天，中位数28天；前三段含首尾均5天，平均5天，现有示例一致。

实施时须分清开始次数、完整段数、可比较间隔数。时长只有开始与结束均确认才计算；缺失/冲突/漏记不能填0。范围变化后统计、来源和摘要数据版本一致。未来参考日期须满足PRD至少3个可比较间隔的条件，不能将描述性统计包装成医疗判断或精准预测。

### 4.4 全局组件与可访问性

- 统一字体、字号、间距、圆角与图标库；正文建议16px等效起步，实际点击区域至少44×44px等效并在真机核验。
- 普通文字对比度目标至少4.5:1；主要交互不可只依赖颜色。原浅珊瑚 `#E97875` 配白字约2.83:1，不能直接沿用为正式小字号按钮文字方案。
- 支持目标机型大字体，价格、截止时间、退款说明和按钮不得被截断或底栏遮挡；输入时考虑键盘和安全区。
- 图标有可读名称，控件的选中、禁用、加载状态可识别；错误与字段关联；弹层焦点/阅读顺序合理。
- 加载、空数据、网络失败、无权限分别呈现；异步任务允许返回和查进度，不能以无限加载封死操作。
- PNG用于设计评审；正式页面使用真实组件与可访问文字，不能整页贴图实现。

## 6. 发布及真实测试门槛

### 设计资料可同步的最低条件

1. U01—U20、S01—S22 文件编号唯一，索引链接无缺失；页面说明与左右视图相符。
2. 示例价格、规格、账期和状态可核对；未把未启用能力显示为已开通。
3. 原PRD仍是业务基线，新增画面不覆盖报价、支付、退款、隐私和到期补救约束。
4. 明确哪些状态由图示覆盖、哪些由文字/状态表补齐；静态稿不被标记为已开发或可交易。

### 开发与试投前的独立门槛

1. 真机验证登录、逐用途授权、拒绝/撤回、数据导出/删除/注销；跨账号、跨对象访问必须拒绝。
2. 支付成功/失败/未知、资格延迟、重复回调、提前续购、断档、外部解约未知均依服务端事实，不能重复扣费或发期。
3. 并发领取、到期竞争、退款冻结、供应超时、履约补救与查单对账通过PRD验收，不能用假成功状态替代。
4. AI任务来源可核对，输入修改/删除/撤权后旧结果不重现；失败与缓存额度口径正确。
5. 提醒预约、平台授权、发送结果各自核验；只在站内生成记录不宣称完成外部提醒。
6. 新增组件完成小屏、大字体、弱网、键盘、安全区与文字对比度测试；栅格稿视觉检查不能代替这些测试。
7. 真实主体能力、供应、支付与必要交易管理配置满足上线要求；经授权的小额真实付款、领取、履约、取消和退款可对账后再试投。

完成图片与文档同步只说明设计资料已补齐，不等于完成上述实现、准入或经营验证。

| 用微信原生授权即可替代业务授权页面 | **仅部分适用。**平台原生登录、地址或消息授权控件可复用，但不能替代健康处理、AI用途及独立代扣等业务说明与有效确认；确认版本和拒绝后路径仍由产品实现。 |
| 网络错误、交易状态用Toast处理即可 | **不足。**Toast可反馈短暂动作，不能替代持续错误说明、原订单查状态、任务恢复与可发现的售后入口。尤其支付未知不能弹一下后消失或引导再付。 |
| 补足图片后就是完整可投放产品 | **不成立。**设计覆盖、接口/状态实现、真实商户准入和交易验证是不同交付层；静态图不能证明业务已运行。 |

因此采纳真实的任务/状态缺口，修正过度概括和重复计数，不按外部列表逐项机械增加路由。

### 7.3 需要修正规则本身的两项问题

#### 退款渠道失败不能直接解除冻结

此项属于真实业务规则问题，不只是少一张图。已批准退款若渠道执行失败、超时或未知，退款业务未必终结，必须保留相应金额预留和`refund_hold`，查询原业务/渠道尝试并安全恢复处理。不能直接恢复领取后又让原退款继续成功。

只有业务已明确拒绝、撤回等终结后，服务端重新核验无其他hold、原资格仍有效或存在有效补救授权，才可以恢复未使用资格。已领取不恢复第二次资格；部分到账不自动恢复或撤销全部权益。PRD、U17说明、S15/S16及验收用例必须一致，不能留有“渠道失败即解冻”的旧句。

#### 下期AI额度刷新必须有已确认的权利依据

“额度不足就显示下期刷新”不适用于所有用户。免费试用耗尽、付费已到期、下一期尚未购买、下一期已付款待生效、真实可用的其他配额规则，需要分别返回与展示。只有已确认未来可获得的额度权利，才显示对应刷新时间和数量；不能凭可能续费推断未来已有权益。

手动记录、历史查看和已有个人资料继续按PRD可用。AI失败不消耗成功额度，同数据版本复用不重复扣生成额度；回顾生成不可用时保留可计算的规则统计。

### 7.4 最终验收口径

- **设计覆盖：**图与文字共同覆盖必要任务、关键正常/异常状态、返回和恢复路径；编号/链接/示例数据一致。
- **实现覆盖：**权限、服务端状态、幂等、任务恢复、金额预留、派生数据删除和错误组件实际运行并通过测试。
- **真实链路：**获得所需主体/支付/模板能力，真实供货可兑现，小额付款、领取、履约、取消和退款可核验对账。

图片增加与文档完善只能证明第一层进展。后两层仍需开发、配置和真实测试，不以“画面已经有成功状态”代替验证。
